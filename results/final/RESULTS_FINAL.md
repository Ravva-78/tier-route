# TierRoute final results (frozen v3 held-out set, 60 tasks)

Run once on `benchmark/tasks_v3.json` (SHA-256 `4a5af81ef68c2003bd4f85978f09af00cb03297c08489d8cad2733282026606c`, frozen and committed before any model call). Routers escalate only on a gold-free verifier (`judge`, threshold 0.5, chosen on the v2 DEV set only). Grading happens after routing. Hosted calls: max_tokens 4096, reasoning_effort low (main), plus always_strong at 4096/default effort as a second baseline; local tier max_tokens 1024. All numbers below are copied from `results/final/v3_tables.md` (generated by `benchmark/run_final.py`) unless marked "derived".

## Findings

1. **Quality is statistically indistinguishable from always_strong.** always_strong (low effort) scored 55/60; cascade 57, rules 56, classifier 55. Paired bootstrap 95% CIs for the quality difference vs always_strong: cascade +2.0 [+0.0, +5.0], rules +1.0 [+0.0, +3.0], classifier +0.0 [+0.0, +0.0]. No CI excludes zero in either direction, so there is no evidence of a quality difference at n = 60.
2. **The routers cost less than always_strong, and these savings have CIs that exclude zero.** Saving vs always_strong (4096, low): cascade 39.4% [22.3, 53.8], rules 38.5% [23.2, 51.2], classifier 19.9% [10.6, 31.0]. Saving vs always_strong (4096, default effort, $0.016022): cascade 60.7% [51.9, 69.0], rules 60.2% [52.7, 67.1], classifier 48.1% [39.0, 57.3]. Cost of always_strong depends strongly on reasoning effort ($0.010372 low vs $0.016022 default).
3. **A router beats weaker baselines on quality, with CIs that exclude zero.** vs random: cascade +8.0 [+3.0, +14.0], rules +7.0 [+2.0, +13.0]; the classifier's interval touches zero (+6.0 [+0.0, +12.0]). vs always_cheap (local only, 43/60): cascade +14.0 [+8.0, +21.0], rules +13.0 [+6.0, +20.0], classifier +12.0 [+5.0, +19.0].
4. **The mid model alone matches the strong model on this set, at lower cost than any router.** Per-tier table: hosted-mid 55/60 at $0.003829; hosted-strong 55/60 at $0.010372. Always-mid would therefore cost 63.1% less than always_strong (derived: 1 - 0.003829/0.010372) at equal quality, which is a larger saving than any router achieved (cascade $0.006290, rules $0.006378, classifier $0.008310). always_mid was not a pre-specified baseline and no CI was computed for it. On this benchmark the value of routing lies in beating always_strong, not in beating a mid-only policy.
5. **Oracle (post-hoc, not deployable).** The cheapest passing tier per task, unsolved tasks sent to the cheapest tier: 57/60 at $0.001041 (workload 46 local / 14 mid / 0 strong). Three tasks (V3-037, V3-039, V3-040, all MBPP) are solved by no tier. Cascade reaches the oracle's 57 but at $0.006290, about six times its cost.
6. **Most failures are MBPP code tasks.** always_strong's 5 misses are all MBPP; cascade's 3 misses are all MBPP; always_cheap's 17 misses are GSM8K 6, MBPP 5, HumanEval 2, extraction 4. The formatting-robust grader changed no result on v3 (orig and robust columns are identical for every strategy).
7. **Bias sweep is mostly flat.** rules: 57/57/56/56/56 correct at bias 0/0.25/0.5/0.75/1.0, savings 39.3%, 41.0%, 38.5%, 34.9%, 21.7%. classifier: 55/55/55/54/55 correct; at bias 1.0 it routes everything to the strong tier (0.0% saving); between 0 and 0.5 its routing barely changes.
8. **Latency figures are not reliable.** Provider calls to the strong tier were rate-limited (HTTP 429) for hours; the provider's retry waits are inside the measured latency (e.g. always_strong mean 12.76 s vs 4.15 s for the same model at default effort). Do not compare latencies across strategies.
9. **Excluding the 3 tasks no model solves** (57 tasks): always_strong 55/57, cascade 57/57, rules 56/57, classifier 55/57, oracle 57/57.

## Settings and prices

Prices come from `config/models.yaml` (USD per 1M tokens; recorded there as verified 2026-10-16): local-small 0/0, hosted-mid 0.075 in / 0.30 out, hosted-strong 0.15 in / 0.60 out. Cost of a call = (tokens_in x price_in + tokens_out x price_out) / 1,000,000, using API-reported token counts; judge-verifier calls to the mid model are charged to the strategy; the local tier counts as $0.

## Methodology lessons: the leaked-escalation bug

* **What it was.** The first v2 benchmark script escalated a request to the next tier whenever `grade_task_v2` said the answer was wrong. That grader sees the gold answer and runs the unit tests, so the router received the answer key after every attempt. Published v2 results (all routers 48/60, escalations equal to under-routed tasks) were therefore invalid.
* **How it was found.** Three very different routers produced exactly the same quality as the oracle, and for each, the number of escalations equalled the number of under-routed tasks. Reading the code showed escalation depended on the grader. Replaying the saved responses showed the escalated task sets were identical to the under-routed sets (`results/v2_audit/AUDIT.md`). With a gold-free verifier on the same responses, quality fell to 35, 42 and 38 of 60 for cascade, rules and classifier (config 1024/default) because the verifier accepts many wrong answers.
* **How it was fixed.** Graders moved to a separate `evaluation/` package; routing code (`tierroute/strategies.py`, `tierroute/verifiers.py`) takes only the prompt and the output; `tests/test_no_leak.py` fails if routing code imports grading code or mentions gold/test identifiers, and runs every strategy and verifier with the graders replaced by objects that raise if touched; four gold-free verifiers were implemented and compared on DEV only; a fresh held-out set (v3) was frozen with a SHA-256 before any model call; the final run was done once.
* **Other lessons.** (a) Identical settings matter: the strong baseline cost $0.010372 at low reasoning effort and $0.016022 at default effort, so savings depend on which baseline is used. (b) A cheaper-looking verifier can be cheaper only because it lets wrong answers through (audit Table 4). (c) A simple single-model baseline (always_mid) must be reported next to routers (finding 4). (d) Check numbers against configuration: earlier reports quoted wrong prices in prose.

## DEV verifier selection (v2 DEV set only; `results/final/verifier_selection.md`)

Rule fixed before running: maximise mean DEV quality over cascade, rules and classifier (cross-validated) subject to at least 20% cost saving vs always_strong on DEV. On DEV (60 tasks) always_strong scored 53/60; heuristic 43.33, strict 44.67, self-consistency (2 or 3 agreeing samples) 45.33 and 47.67, LLM-judge 52.33 (mean over the three routers; costs and escalations in the file). The judge was selected; thresholds 0.5 to 0.9 gave the same DEV quality. The optional Jev verifier was **not run** (no `OPENROUTER_API_KEY`).

## Limitations

* n = 60 and a single sample per task and tier; Groq output varies between runs at temperature 0, so differences of 1-2 tasks are noise (use the CIs, most quality differences vs always_strong include zero).
* One benchmark mix (GSM8K, ARC-Challenge, MBPP, HumanEval, 10 hand-written extraction tasks); results may not transfer to other workloads. Three MBPP tasks are unsolved by every tier and may be hard or ambiguous.
* The benchmark evaluates classifier v2 and rule thresholds 0.50/0.74; the live app (`app.py`) uses classifier v1 and thresholds 0.14/0.32 for its `rules` and `classifier` strategies, so the app's routing for those two strategies was not the one evaluated.
* The LLM-judge verifier adds a mid-model call per local draft; for very short prompts that overhead can exceed the cost of a strong call (live smoke test, `results/final/smoke_live_partial.txt`). Judge confidences on v3 were mostly 0.9-1.0 (cascade final verdicts: 29 at 1.0, 8 at 0.9), so the threshold has little effect.
* Latency figures include rate-limit waiting and are not interpretable (finding 8).
* The strong tier could not be exercised in the live app after the final settings change because of Groq's 200,000 tokens/day cap; strong-tier behaviour is evidenced only by the benchmark calls and an earlier health check. A first live smoke run (`results/final/smoke_live_run1_contended.txt`, `smoke_live.txt`) shows rate-limit and truncation failures on the strong tier.
* Verification code runs example asserts in a subprocess with a timeout only (no memory or filesystem sandbox).
* Cost ignores electricity/hardware for the local tier and uses prices as recorded in the config; Groq prices can change.
* Self-consistency compares code by AST equality (almost always disagrees) and was evaluated on DEV only.
* v2 TEST tasks were visible during development; only v3 is a fresh held-out set, and v3 was never used for tuning. The 3 tasks unsolved by every tier are included in all headline numbers (and excluded in the "excluding unsolved" table).
* The Docker image was never built (Docker Desktop engine not running); `docker compose config` validates.
* Problems during the run are logged in `results/final/problems.log` (77 logged HTTP 429 events from the strong tier and 4 connection or 400 errors; the logger records every fifth failed attempt, so the real count of failed attempts is higher). No call was dropped or filled in; the run completed with all calls real.

## Reproduction

```bash
python -m pytest tests -q                      # 46 offline tests incl. no-leak guards
python scripts/health_check.py                 # Ollama + Groq (add --tiers 0,1 to skip the strong tier)
python benchmark/validate_v3.py                # checks tasks_v3.json against its SHA-256 and the leakage rules
python benchmark/select_verifier.py            # DEV-only verifier selection (live; hours under Groq free-tier limits)
python benchmark/run_final.py                  # single v3 run -> results/final/v3_tables.md, v3_rows.csv (calls are cached)
python scripts/make_figures.py                 # figures from v3_rows.csv -> results/final/figures/
python results/v2_audit/analyze.py             # audit replay of the invalid v2 results
```

Requirements: Ollama running with `llama3.2:3b`, `GROQ_API_KEY` in `.env` (never commit it), Python 3.11. See `QUICKSTART.md`.
